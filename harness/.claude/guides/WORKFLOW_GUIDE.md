# Workflow Guide

How to work on any task in this repo: what to ask before building, the checklist, timing, running agents and which model does what. Read it at the start of every task (subagents with a brief: the checklist, stuck rule and model sections still apply; the brief answers what you would ask).

## Ask for Details
- Before writing code for anything more than a small fix, look for what the request leaves open and **ask**: how it should behave, the numbers (costs, rewards, timings, limits), where UI goes and how it looks, which side runs it, whether data is saved, what happens in edge cases (can't afford, max level, player leaves), and for anything new with a look or layout, whether there's something to point to (`ASSETS_GUIDE.md`, "Reference check"). Don't ask which devices to support: PC and mobile are always supported, console only when the user asks.
- Ask everything in one go, together with any Missing Assets questions (`ASSETS_GUIDE.md`, "Missing Assets"). Use the question tool with 2–4 concrete options per question and your recommended choice first.
- **Ask as many questions as the task needs.** There's no limit on how many: the question tool only takes 4 per call, so send more calls back to back in the same round, before building. Never drop, merge or guess a question just to stay under 4.
- Don't ask what the code, docs, GDD or `GAMEPLAN.md` already answer, and never re-ask something the user already decided.
- **The GDD's answer is the recommended one.** When the GDD or GAMEPLAN's Decisions already decide something and you still ask (a conflict, a better idea), the decided option comes first and is the recommended one, and the question says why it's asked. Any option that differs is labelled **(changes the GDD)** and is never recommended.
- If the user says to use your judgment (or "just do it"), pick sensible defaults and list them at the end instead of asking.
- **Unsure? Ask, don't guess**, even for a small fix, when the answer changes what the player sees, what gets saved, or what you'd build. Only inside a `/build-gdd` / `/revise-gdd` Build step (after the user answered **Build it**) do you use defaults instead, and only for technical details (log them); anything about the game itself waits for the approval step. So ask thoroughly in their Questions step.
- **Never assume the game.** Gameplay, game design, features, content, user experience and the look are the user's ideas. Propose options and get their approval; never decide them yourself, even when a guide or pattern has a default.

### Setup choices can be saved
When the user asks for something different from a saved game default (developers from `/setup`; Studs look, UI tool, reference check, game style and places from `/build-gdd`'s first-run choices), in chat, a GDD or a question round, and it sounds general ("use studs", "I want the studded look in this game"), confirm before saving it, with the question tool and in the task's question round if there is one: **Save it as the game's default** / **Only for this build**. Saved → write it where it's kept (`.claude/skills/build-gdd/RUN_RULES.md`, "First-run choices"; developers: `SharedConfigs/Developers.luau`; Studs: both `SharedConfigs/World.luau` and `references/ART_STYLE.md`) and say so in one line; builders and later sessions only see the saved files. A choice clearly about one thing ("studs on this hut") isn't asked: it goes in that build's brief or ART_STYLE "Exceptions".

## Checklist, Time and Agents
- **Checklist for every task with more than a few steps:** before starting, write one with the built-in task list tool if the session has one, otherwise `checklist.md` in your scratchpad directory. Items are concrete and checkable: the work plus the checks the guides ask for (lint, types, tests, docs, placeholders listed, temp test files deleted, reminders like restarting Rojo or saving the place). Tick an item only once verified, and walk the whole list before the final reply: finish each open item or name it in the report.
- **Elapsed time** (long tasks): note the start time (`date "+%H:%M"`), check it at each milestone against the skill's budget, log every elapsed time and agent duration the harness shows, and end with how long it took. Waiting for the user doesn't count.
- **Running agents:** keep a roster in the checklist (name / id, job, model, start time, status). Continue an agent with `SendMessage` instead of starting a new one, unless its notification shows over ~150k tokens or ~80 tool uses: then a fresh one with a short brief (its context is re-read every step); never start a second agent on work one is still doing, never guess a running agent's result. Do your own non-overlapping work while they run. An agent far past its expected time: `SendMessage` it for status, then fix the blocker or redo that part one model level up. Only you edit shared files while agents run in parallel.
- **Stuck rule (you and every agent; put it in every brief):** an approach that fails twice (the same error, or a workaround that needs another workaround) is dead. Stop it, report what failed and the alternative, and pick another route instead of forcing it. No single step gets more than ~5 minutes of retries.

## Model Routing
Cheapest model that does the job well. When you start a subagent yourself, always pass `model`. Agents and skills have theirs in frontmatter. Code-building work goes to the `system-builder` agent, not `general-purpose` (which carries every tool and connector in the session on every turn).
- `haiku`: finding things, mechanical edits, summaries, docs, commit messages, reading code or text.
- `sonnet`: normal work: features, UI, reviews, edge cases, balance, types, tests, playtests, reading images and models.
- `opus`: planning across many systems, complex systems (custom networking or physics, data migrations), architecture, a bug a cheaper model failed on. `studio-builder` for a full map, `blender-builder` for many or detailed hero models, and `ui-builder` or `figma-designer` designing a new style: `model: "opus"`, `effort: "high"` (never higher).
- Start low and go one level up if a result is wrong or shallow. A single read, grep or small edit: do it yourself.
